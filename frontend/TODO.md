# Real-data HRMS refactor

- [ ] **Project-wide mock/fake audit:** Inspect every page, component, service, and form. Remove hardcoded usernames, email addresses, passwords, faculty names, employee IDs, profile data, attendance, working hours, leave balances, notifications, timetable entries, statistics, fake records, fake-success responses, nonfunctional active controls, and silent mock fallbacks. Load only from confirmed APIs; show empty state for no records and clear error or “Feature not connected” where unavailable. Never invent real-looking records or infer unconfirmed endpoints.
- [ ] **Login and API base:** Authenticate only through `POST /api/auth/login` with `{username, password}`, empty fields by default, actual token and returned role, and appropriate role routing. Preserve real validation, loading, invalid-credentials, server-error and unreachable-backend states. Do not expose role selection or treat frontend role checks as backend authorization. Use a centralized, configurable API base: local `http://localhost:5000` only for local development; remote Preview/publication requires a reachable HTTPS backend URL. Do not fake a successful login.
- [ ] **Registration:** Add username, password, confirm-password, visibility toggle, validation and a working link back to login. Submit to `POST /api/auth/register` and show success only after the backend confirms. Public registration must submit Faculty only; do not permit public HOD/Admin assignment. If the backend cannot enforce authorized privileged-role assignment, explicitly report the required backend change and do not present the workflow as secure.
- [ ] **Forgot Password:** Inspect available backend implementation for a real reset endpoint and requirements. If secure recovery exists, integrate its real flow. If absent or unverifiable, provide a design-ready page with an explicit not-connected message; send no fake OTP/email and show no reset success. State the exact endpoint and secure workflow required.
- [ ] **Faculty modules:** Audit dashboard, attendance, working hours, leave balance/application/history, profile, timetable, notifications and reports. Use real confirmed API data with loading, empty, success and error states; submit only to confirmed endpoint contracts and refresh after confirmed success. Unavailable APIs must be explicitly marked not connected. Never state a leave, attendance or approval action was saved without backend confirmation.
- [ ] **HOD/Admin modules:** Audit department overview, faculty/attendance/working-status/late monitoring, leave decisions, department reports, faculty and department management/HOD assignment, account/role management, attendance rules/geofence and overall reports. Connect only to APIs verified in the backend. Otherwise remove fabricated rows and fake active actions, preserve the layout with clear not-connected/empty states, and do not claim the actions work.
- [ ] **Security and verification/report:** Keep JWT signing keys, database credentials and backend environment variables out of frontend code; never store or log passwords; handle expired JWTs and HTTP 401; require backend authorization for protected data; centralize configurable API requests; remove unused demo data/fallbacks. Build and test only without fabricated credentials/responses. Report mock sources found/removed, login and registration status, password-recovery status and requirements, API-connected vs not-connected modules, remaining connection/runtime errors, and changed source files.

**Current limitation:** The backend source is not included in this frontend project and `127.0.0.1:5000` refuses connections from this remote sandbox. The secure recovery endpoint and live response schemas therefore cannot yet be inspected or exercised. Do not treat this note as evidence that any HRMS API is working.
